# 反馈收集与逐条审核

## 职责与入口

调度 Agent 和接入宿主工具的 GUI、ACP、PTY Worker 先使用 `feedback.history` 分页读取同一应用数据目录的本地反馈和目标仓库已有 Issue，再由 AI 根据问题内容判断是否重复。AI 丢弃重复观察，只用已读完的快照 `checkId` 调用 `feedback.propose({checkId,items:[...]})` 收集最多十条不同草稿；对已存在的待审草稿则用 `feedback.assess` 记录判断。工具只操作本机队列，不创建 Issue；使用习惯、反馈质量和脱敏原则见 `resources/skills/feedback/SKILL.md`，宿主按既有技能供给链部署。工具实际可用性仍由引擎接入和会话权限档决定。

AI 新草稿仅类型和标题必填，其余已知细节按需填写。为兼容旧调用方，工具接受旧的 `impact` 字段，但新草稿会忽略它；已存反馈中的「影响」内容继续保留。

「设置 → 关于 → 反馈」始终提供审核入口；工作台顶栏只在存在待审核或结果待核对的反馈时显示入口及数量。面板集中展示同一应用数据目录下所有工作区、Agent 的反馈，左侧每项固定为标题和状态两行，过长文字以省略号截断，底部可手动添加反馈。手动新增时标题与类型标为必填，类型有默认值；涉及功能、使用场景、实际情况、期望、复现步骤、证据、建议和环境均标为选填，应用版本自动加入环境。只填标题即可保存为本机待审草稿，由 AI 查重后才能进入发送审核；空的选填项不写入 Issue。详情顶部显示反馈标题和状态角标，正文按字段单列展示，每个输入框随内容自动增减高度，由右侧详情整体滚动；输入框不能手动拖拽缩放。删除、查看已发送反馈等操作位于右下角。用户逐条编辑、拒绝、删除或审核反馈，由 AI 比较相似项。审核时字段只读并明确提示提交内容会公开。用户确认后打开 GitHub，使用自己的账号在网页完成提交。编辑或恢复草稿、反馈历史发生变化时，草稿等待 AI 重新查重。审核入口展开为顶栏下方的全屏磨砂层，内容面板使用 `mp-panel-fly` 从上方飞入并按 `--dur-panel/--ease-standard` 进入、按 `--dur-exit/--ease-exit` 退场；磨砂层与面板共用 `mp-scrim` presence，退场不会硬切。

工作台主进程匿名读取 [zhanghexie/muster-console](https://github.com/zhanghexie/muster-console) 的公开 Issues。仓库地址来自 `src/shared/feedback.ts` 的 `DEFAULT_FEEDBACK_TARGET`。「设置 → 关于 → 反馈」提供审核入口和 Issues 链接。正式反馈流程无需令牌或接收服务。选型见 [GitHub 反馈收件选型](../research/github-feedback-intake.md)。

## 数据流与边界

- `feedback.history`、`feedback.propose`、`feedback.assess` 经 `shared/toolDiscovery.ts`、`shared/hostTools/meta.ts`、`capabilities/catalog/feedback.ts` 和 `capabilities/hosts/feedback.ts` 进入 `feedback/service.ts`；宿主绑定真实会话身份，历史快照不能由其他会话复用，来源只留在本地，不拼入 Issue。
- 草稿和状态存于应用 `userData/feedback/queue.json`。同 userData 的 Electron 单实例和同步原子写使本实例的多个 AI 共用队列；不同 userData（包括开发沙箱）不共享本地队列。磁盘损坏时报告错误，不覆盖原文件。
- 仅本机主窗口可通过 `feedback:*` IPC 审核或打开 GitHub 提交页。`FeedbackCenter.tsx` 展示待发内容，内部 Issue 标记不显示给用户。修改草稿、历史或目标变化、审核过期及应用重启都会使原审核失效。
- 反馈审核的内容卡使用 `mp-panel-fly` 保持实底滑入滑出，后方独立的 `mp-scrim` 磨砂遮罩负责淡化。退场立即释放命中，面板保留到过渡结束。
- `feedback:createManual` 只允许主窗口调用，逐项校验并脱敏人工填写的反馈字段，持久化为 `aiChecked: false` 的本地草稿并请求 AI 查重；同名草稿也交由 AI 判断，不直接合并或创建远端 Issue。旧版手动输入的自由正文保留原文，并可补充各分项。新建草稿同样要经逐条审核和用户确认。
- 字段编辑通过 `feedbackFormatting.ts` 在界面上拆分和组合正文，再由 `feedback:updateText` 校验、脱敏，更新标题与完整 Issue 正文；原先各字段清空，避免用户删去的内容残留或意外发出。已有反馈的「影响」内容继续展示并保留，用户清空后不再发送；新建手动反馈不提供影响输入项。旧版自由编辑正文无法识别的内容保留在「反馈正文」字段中，重新组合时不丢失原文。主进程向网页交付审核内容并附加内部对账标记，用户可在网页继续编辑。AI 查重读取本机保存的正文。
- 反馈正文与手动新增共用 `FeedbackCenter.tsx` 的受控文本框。支持 `field-sizing: content` 时由浏览器计算内容高度，保持表单全宽和最小高度，无需设置行内高度或注册 `ResizeObserver`。旧浏览器由已有逻辑在值更新和宽度变化后测量，隐藏时跳过测量，恢复可见宽度时重新计算。
- 用户确认后，`feedback:delete` 按记录 ID 与版本删除本机队列记录；删除后自动选择剩余记录，不调用远端删除接口。已提交记录的确认框明确说明仓库 Issue 保留；已打开 GitHub 或结果不确定时说明删除会失去核对记录；正在提交的记录不能删除。删除会改变本地历史并使已有 AI 查重快照失效；被删除的本地草稿不再参与查重。
- 直连适配器读取仓库所有开放及已关闭 Issue，不以标题相似度过滤，再将本地及远端记录分页提供给 AI；不提供来源会话、工作区名称或令牌。列表正文最多返回 4000 字符，截断有标记，AI 可用相同 `checkId` 和 `detail` 分段读取完整正文；远端正文变化会使详情和快照失效。每页按 JSON 实际长度留在工具输出预算内，正文是不可信数据。AI 应在证据不足时不判为不同问题。最多读取 50 页、每页 100 条，超限或远端读取失败不能视为无重复。
- AI 判断使用绑定调用者、10 分钟有效的完整历史快照；本地其他 AI 并发写入或远端历史变化会使快照失效。打开 GitHub 前再次验证历史，变化后自动让调度重查；归一化标题相同仍是强制去重兜底。AI 的语义判断可能出错，不同应用实例、电脑或其他工具同时创建 Issue 也无法保证跨机器原子去重。
- `feedback/aiRecheck.ts` 在需要重查时向空闲调度发起宿主回合；调度读取历史并用 `feedback.assess` 标记重复或完成检查。宿主排队不等于执行完成，直到对应工作区调度空闲后才判断是否完成；失败或未完成保留草稿并提示。模型、网络不可用或内容不足时不会假装查重成功。
- `feedback:submit` 接收当前草稿版本和有效的 reviewId。主进程重新校验查重历史，再调用 Electron 的默认浏览器适配层打开仓库的 `/issues/new`。短反馈预填标题和正文。编码后的 URL 超过 2000 字符时，确认页显示「复制正文并打开 GitHub」，先复制完整正文，再打开只预填标题的页面。用户在 GitHub 的 Write 页签粘贴正文后提交。Windows、macOS 和 Linux 共用 Electron 的默认浏览器及系统剪贴板接口。Linux 依赖可用的 X11 或 Wayland 会话和默认浏览器。复制或打开失败时保留待审核草稿并提示重试。
- 「已打开 GitHub」状态持续展示空正文的处理方式，提供「复制 Issue 正文」。`feedback:copyIssueBody` 校验本机主窗口、草稿版本和状态，根据已保存的草稿复制完整正文及对账标记。应用重启后仍可复制已经打开过的草稿。复制成功或失败均有提示。
- 打开浏览器之前把目标写入本机状态。浏览器打开后记录为 `opened`，用户在 GitHub 网页提交后通过 `feedback:reconcile` 读取仓库，找到正文标记才记为 `submitted` 并保存 Issue 链接。用户若关闭网页，可在核对标记后恢复草稿。网页删除标记则无法自动关联。应用在打开过程中退出时标记为 `uncertain`，旧版已提交记录及链接继续可用，旧目标的不确定提交需在原仓核对。
- 草稿遮蔽常见凭据形态及进程环境中的已知凭据；不自动附带完整对话、项目文件或截图。规则无法识别所有私人信息，用户提交前仍需检查。

## 旧版本数据

原有队列继续使用，旧目标的 AI 查重结论在审核时与新的远端历史核对。公开流程不访问旧版的反馈令牌，历史文件和系统 Git 凭据不进行迁移。独立反馈中继默认访问 `zhanghexie/muster-console`，自建实例可通过 `FEEDBACK_REPOSITORY` 指定目标。中继仍由部署方单独配置凭据。

## 验证与维护

主进程用例覆盖匿名读取、限流、审核后打开网页、长文复制与重启后重新复制、剪贴板和浏览器错误、回执对账。组件用例覆盖审核入口、公开提示、空正文指引、复制反馈、网页提交状态与恢复草稿。`test/e2e/feedback-review.spec.ts` 在隔离 Electron 中使用真实组件和 IPC 验证短文预填、长文重新复制和提交核对。GitHub API、默认浏览器启动和系统剪贴板由夹具模拟。

自动高度回归见 `test/unit/feedback-center.spec.tsx`。`test/fixtures/feedback-visual.tsx` 配 `feedback-autosize-scenario.mjs` 使用生产面板和 CSS，在 macOS Chromium 深浅主题的 780 和 320 px 视口检查长文换行、清空收缩、运行中改变宽度、隐藏期间收到程序写入后重显。旧浏览器分支通过关闭 CSS 和 JS 的原生能力入口模拟，尺寸和 `ResizeObserver` 仍使用真实 Chromium。本专项未实测旧浏览器、其他平台或 Electron 原生窗口。
