# 持续上下文的业务审批代理

安全子系统代替人判断低频业务事项，按工作区持续对话；日常 Shell、文件编辑和已批准 App 的普通使用不逐条送模型。执行权限仍由原引擎、只读模式、目录与账户权限控制，不覆盖外部 CLI 自行执行的所有命令。实施与验收。

## 审批范围

`safety/policy.ts` 使用显式业务动作目录，不再依据任意 dangerous 标记或 Shell 字符串送审。界面直接发起的操作由主进程可信 IPC 入口确定为人工操作，不调用安全审核；AI 工具与来源不明的后台发现仍按各自的业务和信任门审核。操作参数不能自报为人工。

| 范围 | 入口与行为 |
|---|---|
| 合入代码 | AI 调用 SessionsService.integrateWorktree 时提供会话、工作树、仓库提交与变更清单，审批模型按需读取本次快照中的 diff、状态和提交记录，审批后复核；用户看板验收直接执行，二者都经过原 Git 预检 |
| 永久删除会话 | AI 调用时汇总精确目标及后代、核查归档/仓库材料并审核；人工点击删除直接执行。两者都要求目标已归档且属于同一工作区；内部系统清理仍用 close |
| 重开 CLI 会话 | sessions.restartConversation 会丢弃续聊上下文，调度工具执行前走安全审核；拒绝或取消不重开 |
| 新App/定义更新 | AI 安装或实质更新自制定义前审核；人从共享库安装或启用直接执行，完整定义与随应用分发版本一致的内置 App 和相册模板也免审核。纯名称/版本变更免模型，行为或权限变化重审；已批准同一定义启停复用指纹 |
| 扩展/动态工具/工作流 | AI 首次或内容变化时审核指纹信任，已信任内容运行不重复送审；用户在工作流面板点击信任直接记录当前指纹。可按完整内容或宿主记录指纹确认的内置扩展首次安装、更新免审；扩展目录监听无法识别外部文件修改者，无法确认归属或已修改的内容仍审核；证据获取失败明确转人工 |
| 配置/自动任务 | AI 修改模型供应商与默认模型、运行时、邮箱凭据授权或创建/实质修改自动任务走对应门；用户直接在界面保存设置或任务不送审；纯名称修改不送审 |
| 日常操作 | Shell/文件/搜索无安全模型调用；default/auto及计划执行态Shell直接执行，ask/plan探索态只读限制与用户显式ask/deny仍保留；普通App记录和发送沿已有能力权限 |

Catalog executor 展开真实 action 后分类；会话/App 业务门和代码信任门不重复审核。`ipc/workspaces.ts` 的自动任务与 Runtime 设置直接调用服务；模型调用仍经 Catalog 审核。会话、人侧工作流信任与手机 App 库入口由 IPC 固定内部来源，跨线程传递时默认为 AI；工作流取消时用户选择关闭会话的来源也随迟到补偿保留。常规目标校验、能力权限和其他操作确认不因跳过审核而移除。

审批期间同时绑定会话生命周期令牌；会话归档后即使恢复并复用同一对象，先前待完成的审批上下文仍失效。没有已注册会话的独立宿主调用继续使用其原有身份与作用域校验。

主进程可将确认标为 `localOnly`：请求正文只发送到桌面窗口，不向网页客户端广播，且仅接受目标桌面窗口主 frame 应答；普通确认维持既有桌面与网页并行应答行为。桌面证据仅允许本机确认，主进程核对 PNG 摘要、完整解码及区域尺寸，图片未成功加载时界面禁止批准。模拟回归覆盖网页与其他 frame 拒绝；Windows 真实 Electron 验证了截图显示与合法主 frame 的应答，macOS/Linux 未真机验证。该证据确认入口尚未连接实际桌面输入后端。

宿主自带技能由部署流程直接安装和更新，不进入安全审核。App 和扩展的内置资源免审依据完整定义或源码指纹，而非仅凭名称或 ID；用户或第三方修改后的 App 和扩展继续适用原有审核规则。

## 持续会话与存储

审批记录继续保存原始原因，模型或用户提供的理由不会改写；人工确认框和审核对话只在展示时翻译可识别的宿主原因及外层文案，并保留其中的模型理由、目标和原始错误。确认按钮的宿主动作也使用当前语言；未知动作保留原文。邮箱连接配置审批摘要在动作和完整摘要均匹配宿主生成内容时翻译，其他摘要保持原样。对话按消息来源和请求身份区分宿主文本与自由聊天，英文状态提示使用已知状态的展示名称；切换语言会重新投影已加载消息，不改写快照、审核结论或回执。

safety/bindings.ts保留单个reviewer工厂，pi.ts按工作区复用专用Pi SDK会话。用户聊天、规则设置和后台审批在service.ts的同工作区队列串行运行；不同工作区不共享历史和规则。

空闲60秒释放SDK对象；24轮或累计输入接近有界预算时换代，恢复时加载持久近期消息、带出处的历史摘录和有效规则；会话存续时增量补入新消息，包含模型回合之外发生的人工决定。Git 证据工具的聊天卡仅记录调用状态与参数，正文留在当次审核内存。使用该工具的物理会话在本次审核结束后释放；逻辑会话仍通过持久消息恢复。普通审核每次最多6次模型请求、默认45秒；需要按需查询 Git 证据时最多12次、默认90秒。单次 SDK 序列化上下文上限为 262,144 字符；上下文超限、输出截断、取消及上游调用错误分别显示原因，上游错误先脱敏和截断。审批排队默认5分钟，用户答复默认30分钟，分别计时。

存储为userData/safety/<workspace哈希>/conversation.json，包括有界审批记录、脱敏消息、摘录、规则和版本。旧audit.json只读导入历史，不恢复通过票；重启将未完成审批标为失败，需要原入口重新提交，不自动重放副作用。规则落盘失败回滚内存及版本，并阻断该工作区的自动授权，不能出现报保存失败后仍使用新规则的情况。审计写入复用原子临时文件和有界瞬时锁重试，保留私有文件权限；彻底不可用时业务门改为独立人工确认，明确告知本次记录无法保存，仍复核目标与取消状态。

## 用户对话与规则

面板标题下只显示一条连续对话，直接复用 `ChatSurfaceView`、`ChatTranscript`、`AgentComposer` 和既有 motion；审批记录与放行规则仍由中心/后台状态提供，不再在审核面板中增加第二、第三个页面。草稿、状态、代次和迟到响应按工作区隔离。打开/收起仅读状态，不启动模型；关闭不清上下文。顶部原刷新按钮改为重置，复用 ChatResetDialog，先说明会停止当前处理、取消未完成审批并清空对话，保留放行规则与审批事项记录；取消不调用清空，确认后才执行 safety:clear。底部不再提供直接清空入口；失败保留确认框及实际错误，工作区切换或面板收起使旧确认失效。

审核回合的 `message_update` 文本增量、工具开始/结果和错误由 `safety/pi.ts` 转成 `SafetyStreamEvent`，`safety/service.ts` 以 `GuiChatMessage.parts` 节流推送 `safety:changed`。因此模型正文与工具卡在回合进行时就出现在同一转写流中，结束回合只补齐最终裁决，不另起一条快照式回复。审核 surface 的模型状态和模型切换委托调度 workspace surface，输入框使用同一个模型按钮和 `chat.switchModel` 链路。

safety:send/stop/clear/setRuleEnabled由主进程认证的用户IPC提供，不暴露为Worker工具。普通聊天正常回复，不强制裁决。规则不再单独占一个面板页，而是由用户在连续审核对话中明确提出、代理调用 safety_rule 后保存，包含原始用户依据、动作范围、版本和启停状态；只有当前可信用户聊天允许safety_rule写规则，代码、外部材料、其他Agent说明和历史个案不能自授规则。

宿主业务门在每次实际送审时建立 `snapshot.records` 记录，后续写入状态、裁决原因、模型和时间；最多保留最近200条。审核面板只呈现连续会话，记录和规则仍由安全服务快照及其他管理入口读取，数据持久化于上述 conversation.json，不从聊天正文临时推断规则或伪造事项。

系统自动送审只允许两种模型结果：allow（通过）或 concern（需要人工审核并附具体理由）。提示词和工具 schema 均不提供直接拒绝选项；要求只调用一次 safety_decide，理由描述事实、风险或缺失材料，不向用户提问，不在工具外输出聊天正文。宿主将自动审批消息固定显示为「通过」或「需要人工审核：理由」，忽略自由文本；用户主动发言仍正常对话。模型返回旧 deny、非法回执、只有聊天正文、模型异常、模型超时及排队超时均走人工交接。

concern 和上述故障立即调用该操作的人工确认弹窗，释放模型队列；扩展复用完整包审查框并直接显示疑点。用户在弹窗批准或拒绝后直接完成原请求，不再向模型求批准，也不要求打开审批聊天。业务入口没有专用确认框时，宿主提供默认确认框；确认通道不可用、失败或超时则明确结束为未授权，不保留无法处理的隐藏待办。

每轮模型输入明确区分 system_approval（系统自动申请）与 human_chat（用户主动发言）。持久消息的 origin 区分 approval_request、user_chat、reviewer、human_decision、service；人工决定带 requestId 和事项，后续正常对话能识别已发生的决定，但不能把旧决定当成新操作授权。聊天用于讨论与规则设置；旧 requestId 回复接口只返回当前事项状态，不重启模型审批。

## 执行与隔离

空资源Pi会话仅开放 `safety_decide`、受限规则工具和 `safety_evidence`，不加载 AGENTS/skills/扩展/模板或通用文件/Shell业务工具。`safety_evidence` 只接收当前系统审批请求 ID 与宿主生成的仓库/文件序号，分页读取会话合入或删除的本次 Git 快照；不能指定任意路径或执行命令，用户聊天和其他审批类型不能使用。注入登记为 safety.reviewer.system/request/tool-schema/chat/rules-tool/history/evidence-tool。模型沿当前 workspace 调度配置和全局配置选择，审核设置不提供第二个模型选择器。

allow/concern绑定宿主请求ID、参数指纹、代次和规则版本。allow执行原操作；其他情况交人工，模型不能直接拒绝。人工拒绝、操作取消和执行器硬性权限限制仍有效。人工决定仍复核当前作用域、目标指纹和规则版本；审计写入失败不能生成自动许可；人工门明确说明记录不可保存后，由用户直接决定本次操作。重复或非法裁决不能由先前allow覆盖。

取消、停止、清对话、工作区/会话失效以及参数/规则变化使旧回执失效；超时或停止后的迟到工具不能写规则，迟到消息不能恢复旧会话或销毁后续新会话。人工确认接收请求专属 AbortSignal；结束、停止、重置、失效或超时后发送 ui:confirmClosed 移除桌面/Web 对应弹窗，迟到点击无效。渲染窗口关闭、刷新或崩溃解除等待；确认准备工作有界。审批代理不执行副作用，执行器等待许可并复核实际目标。

`GitService.approvalEvidence` 提供源/目标提交、提交范围、diff、工作区状态与完整哈希，原有有界预览继续用于本地审批前后比对。宿主将本次 Git 文本去重并只保存在请求内存中（累计最多 400 万字符），初始消息提供有界仓库及变更文件概况；模型可按仓库、diff 类型和文件序号分页读取完整捕获内容（每页最多6000字符），状态和未跟踪文件清单按页读取。会话 cwd 位于仓库子目录时先解析仓库根，避免重复或伪造不可用仓库。删除操作的捕获不完整、仓库不可用，或合入操作的任务 diff 捕获不完整、任务仓库不可用，以及存在相关 diff 却未读取时，模型的 allow 回执不能自动放行，转人工处理；长 diff 至少读取256字符或读完全段较短内容才计为已读取。此守卫不要求遍历所有文件或完整 diff，审阅深度由模型判断；单次模型上下文仍受上限约束。非 Git 审批继续使用原有证据路径，尤其扩展包完整审核不降级。untracked普通文件校验后顺序哈希，符号链接仅哈希链接目标文本，特殊节点拒绝；工具不提供未跟踪文件正文。测试证据为 verified-pass / verified-fail / not-collected 三态；Git 探测返回 not-collected，不把申请者自述算作验证。后台任务退出码尚未绑定被测提交，不能直接升级为 verified-pass。

多仓查询省略仓库编号时，只有全部仓库的所请求 diff 或提交文本哈希一致且均可用，才自动选择一份等价快照，响应带实际仓库编号；状态和未跟踪文件仍需明确选择。内容不一致或仓库编号不存在时，工具返回可选仓库编号，允许模型重选，不把无效编号当路径；文件编号缺失或无效时返回当前 diff 的文件候选。选中的仓库确实不可用时返回采集错误供模型给出具体疑点；未解决的仓库/文件选择或不完整快照不能自动批准，即使此前已经读取其他内容。模型必须收到证据工具的结果后才能批准；同一轮并行发起读取与批准、或者同轮假装修正未见到的选择错误，都不能生成自动许可。

## 合入证据分账与分级

`SessionsService.approvalSnapshot` 根据宿主工作树映射标记 `task`、`target-checkout`、`shared`；未能确认归属的根另标 `roleUnknown`。合入范围只依据 `task` 的源/目标提交间 diff；目标检出的未提交、暂存、未跟踪文件及 ahead 计数属于用户日常 WIP，标为 informational，不能单独作为污染风险否决。目标材料仍保留在完整快照中，审批后变化照常使许可失效，Git 重叠与冲突预检不变。删除操作仍检查完整工作区材料。

`gitPolicy.ts` 在服务端将关键与辅助证据分开：任务 diff 缺失或捕获不完整、源/目标提交不明、任务改动触及安全/权限/审批链路，强制把 allow 转为 concern；证据工具失败仍交人工。任务路径守卫覆盖 safety 目录、权限/审批命名路径和已知会话合入入口，模型仍负责语义审查，不宣称路径列表涵盖所有可能的安全变化。额外仓库不可用、目标检出脏、tests=not-collected 记入 reason，不强制 concern；模型自身 concern 从不被宿主反转为 allow，仍直接开人工确认框。没有可确认的任务仓库不是污染证据，但源/目标身份缺失仍属于关键缺口。

会话 liveStatus.summary 与 GUI 最近完整回复作为不可信 `delivery`（最多 8000 字符）随现有 `safety.reviewer.request` 进入审核；摘要、操作摘要或合并说明中声称测试通过而没有对应证据时必须 concern。服务端拦截明确的中英文通过声明，模型负责其他表述；这不把交付自述变成测试回执。verified-fail 强制 concern，not-collected 且未声称通过可自动通过。当前没有接入可验证被测提交的测试回执采集器；CLI 没有结构化完整回复时只采用已上报摘要，不从混杂终端输出伪造交付结论。

回归 `test/safety-integration-classification.mjs` 从真实 `approvalSnapshot` 方法装配夹具，串联证据 collector/view 与安全服务，覆盖目标脏允许、目标安全文件 WIP 不冒充任务变更、任务安全变更转人工、无测试证据的通过声明、关键材料缺失、辅助仓库失败与模型 concern 不被覆盖。改动前的快照方法会使「目标脏允许」断言失败，当前实现通过这项验证。这是离线裁决夹具，不等同真实模型回归或跨平台真机验收。

## 设计初衷（2026-10-26 与用户定稿）

> 依据 campaign-intent-drafts/D10-D14.md 草案定稿（用户 2026-10-26「不抽查直接定稿」）；歧义点处置：22 项卡片决策＋长尾按草案推荐，明细见专项账本「意图定稿决策」节。

- 为谁/什么场景：按工作区持续对话的安全审批代理，替人判断低频业务事项——合入代码、永久删除会话、新 App 安装、扩展/动态工具/工作流信任、模型供应商与自动任务等配置实质修改；日常 Shell/文件/已批准 App 普通使用不逐条送模型。
- 为什么这样设计：显式业务动作目录（不按 dangerous 标记泛化送审，防审批风暴）；可信界面发起的人工操作直接执行，AI 操作由宿主按目录送审，未知来源的扩展自动发现仍审核；规则只能由可信用户聊天设置（safety_rule），代码/外部材料/其他 Agent 说明不能自授；审批绑定请求 ID+参数指纹+代次，多项待办不共享一句「同意」；重启未完成审批标失败需原入口重提，不重放副作用。
- 明确不做：不覆盖外部 CLI 自行执行的命令（执行权限归原引擎/只读模式/目录账户权限）；审批代理自身不执行副作用；规则落盘失败回滚并阻断该工作区自动授权（不出现「报保存失败仍用新规则」）；记录存储故障明确转独立人工门，由用户决定本次操作。
- 歧义点：无真决策（审批范围、超时语义、规则授权红线均为 2026-10-25 实施计划定稿；该功能刚落地，review 侧重验收实施计划承诺）。
