# Core 会话上下文压缩

内置 Core 的 GUI Worker 和调度 Pi 会话共用 `src/main/agent/coreContext.ts`。GUI 在 `workerEngine.ts` 装配扩展，调度入口为 `piProvider.ts`。两侧都在 Pi 原生工具清单注册 `core_context`。策略使用 Node 与 Pi SDK 的跨平台接口。

## 模型收到什么

1. 在一个工具组结束时，刚返回的结果先按原路径交给模型。后续完成的模型调用表明它已消费上次的结果，Core 才考虑摘录。同一用户输入内的多个工具轮也适用。选取范围止于当前用户消息、已有改写目标或检查点。自动摘录针对已知读类、轮询及成功的 Shell 文本结果；独立保留报告失败的结果。优先保留连续重复行的次数、顺序以及全部不同的行。对于无法通过消重明显缩短的文件与检索结果，留待模型判断。若诊断或受保护行超出摘录预算，保留全文。入选的结果保持原工具角色、调用 ID 和顺序，正文带稳定来源 ID。
2. 新用户输入前和完成的工具组末尾，Core 扫描已经结束的工具组，留出最近的工作。候选区间按实际投影的 UTF-16 字符估算净收益，扣除必须保留的用户原话、错误和诊断引文，另预留 2,048 字符给摘要。通常净收益达到 32,000 字符即可提示；已用 token 达到模型窗口 × 配置压缩比例 × 0.72 时，降为 4,096 字符。同一区间起点只有在收益再增长至少当前门槛的一半且至少增长上次估值的四分之一时才重复提示。提示并入正常调用，模型判断工作是否已经结束并编写摘要。提交时再次校验实际收益、边界与工具配对。
3. 模型可原位摘录单条结果、折叠整个前缀，或用左闭右开的 `[start, keep)` 折叠中间一段。遇到图片、宿主内容或中断的工具组，会继续寻找后面的完整文本区间。前缀和单条结果沿用 Pi 的 `compaction`、`context_edit`；区间在 Pi 分支中原子追加一个带来源 ID 的自定义条目，投影时只在起点放入摘要。展开区间另追加一个撤销条目。重开、分叉、下一次模型调用共用同一投影。SDK 安装补丁位于 `scripts/patch-pi-context-range.mjs`。
4. 原会话树保留来源，检索范围为当前叶子的祖先路径。工具已自行截断的内容以它实际返回给模型的文本为界。GUI 开启「模型请求」记录后，可在实际 HTTP 正文中定位生效的摘要并按来源查看原文。原生超窗恢复和手动全量压缩仍可用。

## 原生工具

内置 GUI 的[模型请求面板](model-request-viewer.md)直接显示本次发送采用的摘录、工具结果摘要和阶段检查点，支持按来源对照原文。面板也可触发当前会话的原生全量压缩。

| action | 用途 |
|---|---|
| `status` | 查看占用、近期检查点和分页保留边界。最近的边界排在最前，每项附消息角色。边界预览用于选区，服务端在提交时作最终检查 |
| `fold` | `keep + summary` 概括该条目前的完整前缀；可选 `start` 指定包含起点的局部区间；`id + summary` 只替换一个可摘录的结果。tool 先回报提案，成功的工具组到达原生边界后才提交 |
| `sources` | 用检查点 `id` 读取本代来源列表、上代 ID 与页游标 |
| `search` | 用字面 `query` 检索分支中的原始公开文本和历史检查点。返回稳定 ID、命中位置与短摘录 |
| `read` | 按来源 `id` 和 UTF-16 字符偏移 `offset` 取回原始文本页。后续页从返回的 `next` 继续 |
| `expand` | 将活动的前缀检查点展开一代，或还原一个活动的局部区间。旧块仍可通过 `sources/read` 查询。一次只提交一个历史变更 |

自动运行遵守 `autoCompact.enabled`，`micro.enabled` 控制机械摘录。GUI 按连接接收宿主配置并尊重模式的 Pi 压缩开关。显式历史查询与模型主动调用工具独立于自动触发。旧模式的 `contextTrim` 属于单次请求的字符上限。`read` 按该上限计算含 JSON 转义的页长，保留下一页游标。`status/search/sources` 也按完整 JSON 长度分页，必要时缩短预览。`status` 的续页游标锚定当前分支上的位置，后续查询自己新增的消息不会改变旧页。搜索跳过恢复工具的调用参数及结果，避免查询词被误当成历史证据。用法随宿主安装到 `~/.muster/skills/core-context/SKILL.md`。调度原有微压缩按 Pi 最新投影估算剩余结果的大小。

## 验证

`node test/core-context.mjs` 在临时目录启动真实 Pi、原生文件工具和本机 HTTP 端点，检查实际请求、工具配对、三代折叠与展开、诊断保留、重开、分叉和原生全量压缩后的原文取回。将 `CORE_BENCH_DSH` 与 `CORE_BENCH_BILLION` 指向调研记录中的两个固定提交，可以同时执行上游摘录和三级折叠的同输入机制对照。默认使用固定模型回复，离线运行。

要跟随当前 Core 全局默认，将 `CORE_BENCH_USER_DATA` 指向运行中工作台的应用数据根，脚本读取选中的服务商和模型，并使用同一工作台同步给 Core 的认证和模型目录。独立 Pi 对照可改用 `CORE_BENCH_PROVIDER` 和 `CORE_BENCH_MODEL`。两种入口只向模型发送合成样本。2026-11-14 在 Windows 上，分别用工作台当前默认的 `qwen-token-plan-cn/qwen4-max-preview` 和独立 Pi 的 `deepseek/deepseek-flash` 读取同一份 10,271 字节的日志，分别询问中央的警告码和一条普通记录的完整值。两次运行在五种输入上得到相同分数。下表记录每个模型各自答对的字段数。

| 输入 | 直接回答 | 直接答漏后补回同一原文 |
|---|---|---|
| 完整原文 | 2/2 | 无需取回 |
| Core 摘录（217 字节） | 2/2 | 无需取回 |
| DSH 摘录（222 字节） | 0/2 | 2/2 |
| Core 三级折叠 | 1/2 | 2/2 |
| billion-context 三级折叠 | 0/2 | 2/2 |

三级对照给两边相同的阶段摘要，以观察各自额外携带的证据。补回原文由夹具发起。另一个独立的真实 Pi 会话中，DeepSeek Flash 收到阶段折叠要求后自行选择边界、撰写摘要，随后用 Core 工具检索原文并答对两个字段。早期复跑里，较宽松的答题格式曾让 Core 摘录组在补给原文后仍得 0/2，另一次真实会话里模型分段读了文件首尾，两个返回值均低于自动摘录门槛，也没有读到中间证据。也观察到模型为过短前缀提出折叠，未达到净节省门槛。状态查询据此增加了边界角色，优先列出最近边界；拒绝原因提示可重选边界。最终夹具明确了字段格式、单次完整读取范围和待折叠的已完成阶段，并保留工具轨迹。表中列出固定题面的一次运行；两个实验都只覆盖这份日志。多任务非劣性、自然触发率、缓存计费、延迟及 macOS/Linux 真机验收见对标方案。

在 Core 当前默认的 Qwen 上，另行运行了真实 Pi 工具循环。第一次要求模型写交接说明，回复触及输出上限，留下的可见历史太短。模型随后调用 `fold`，净节省检查拒绝了提案。第二次使用同一份日志，再加 72 条互不重复的合成记录作为已完成的阶段。Qwen 实际调用 `status`、`fold` 创建了检查点，再调用两次 `search` 和一次 `read`，准确回答了警告码和普通记录。两次均由测试明确提出折叠要求。此路径与表中由夹具补回原文的实验独立。

Windows Electron 专项命令为 `npm run test:e2e -- core-context.spec.ts`。它通过真实 GUI 会话读取合成日志，让本机模型端点从下一次请求的摘录中取得来源 ID，再调用 `core_context read` 并逐字核对原文。
