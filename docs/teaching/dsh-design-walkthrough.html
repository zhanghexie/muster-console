Station 0

一个能跑的裸脚本

任何 agent 的本质，几行就写完了——循环调模型、执行工具、把结果喂回去：

// main.ts —— 我们的第一版
const tools = { read_file, run_bash }

while (true) {
  const reply = await llm.chat(messages, toolSchemas)
  if (!reply.toolCalls.length) break
  for (const call of reply.toolCalls) {
    const output = await tools[call.name](call.args)
    messages.push({ role: 'tool', content: output })
  }
}

↑ 它能跑！记住这个文件的样子，接下来整栋大楼都是把它翻新。

痛点预告 所有功能的修改点都长在同一个文件里：tools 对象是写死的、模型是写死的、 想在调用前插一段审批逻辑也只能改循环本体。一个人玩没事，二个人协作就打架，一百个插件没法想。
Station 1 · 插件化

每加一个工具都要改核心 → 一切皆插件

痛点 加个搜索工具、换个模型供应商、出一份"不带 bash 的精简发行版"……全都要动 main.ts。 十个人改同一个文件就是十份 merge conflict；发行版只能靠剪刀裁剪核心。

关键翻转：把 main.ts 由内向外翻

原来是我们 import 工具；现在改成工具来注册自己。核心只提供一个登记处：

// 核心暴露登记 API；每个能力是一个独立文件
export function apply(ctx: Context) {
  ctx.tools.register({ name: 'run_bash', schema: {...}, execute })
}

再用一份清单声明"这个产品 = 哪些插件"——这就是你在 dsh 里随处可见的 cordis.yml：

# cordis.yml：dsh-base 发行版的本质就是这四行的加长版
- name: '@deepseek-ai/dsh-tool-fs'
- name: '@deepseek-ai/dsh-tool-bash'
- name: '@deepseek-ai/dsh-llm-deepseek'
- name: '@deepseek-ai/dsh-web-app'
解法 文件里没有任何框架引导代码；插件只描述自己的贡献，cordis.yml 就是产品形态本身。 web 版 / headless 版 / 你自定义的版本，差别只是清单不同。"一切皆插件"说的就是这个翻转。

Station 2 · 服务与依赖注入

插件之间怎么互相找？→ ctx 键与服务 + inject

痛点 第 1 站之后出现新问题：bash 工具需要知道工作目录（文件系统插件管的）， 日志插件想知道工具被调了没。如果 bash 直接 import './fs-plugin'， 耦合又回来了——换掉 fs 实现还得回头改 bash。

解法：共享能力挂到 ctx 的键上，消费方只认键名

// 提供：往 'tools' 键上放一个服务
export function apply(ctx: Context) {
  ctx.plugin(ToolsService)   // 注册名就叫 'tools'
}

// 消费：只声明"我要 'tools'"
export const inject = ['tools']
export function apply(ctx: Context) {
  ctx.tools.register(myTool) // inject 保证这里 ctx.tools 已就绪
}
  • 加载顺序由依赖决定，不由清单顺序决定：缺依赖的插件停在 ⏳ PENDING，依赖就绪自动唤醒。
  • declare module 声明合并把服务合并进 Context 类型——运行时按名字找，编译时有完整提示。
  • 所以 ctx.fs / ctx.llm / ctx.shell / ctx.agents 没有任何魔法，全是普通的服务键。"扩展点 = 往对应的键注册"就是这么张表。
动手玩下面这个「迷你容器」是真的会解析依赖的： 勾选/取消 yaml 清单里的插件，观察右侧 fiber 状态和日志怎么联动。

Station 3 · 生命周期

卸载之后留下满地僵尸 → effect 与 fiber

痛点 插件支持热重载了（改文件立即生效），但你的插件开了定时器、加了监听器、连了 socket—— 重载一次泄漏一批。谁来清理？

解法：注册即效应（effect），死则级联清场

export function apply(ctx: Context) {
  // ctx.on / register 本身就是 effect：
  // 插件死了，监听器跟着死，永远不用手写 removeListener
  ctx.on('tools/call', logToolCall)

  // 框架外的资源显式包一层，返回释放函数：
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 1000)
    return () => clearInterval(timer)  // 卸载时框架替你调
  })

  // 子插件的"存活凭证"叫 fiber，可主动 dispose：
  const fiber = ctx.plugin(someChildPlugin)
  // fiber.dispose() → 它注册的一切连带消失
}
解法 粒度单位是 fiber，清理是级联的：销毁插件纤维将自动注销它的全部贡献。 所以热重载免费获得正确性——旧的卸干净，新的再上来； 实验里你取消一个提供方时看到的那种"连带卸载"，用的正是同一套机制。

Station 4 · 事件系统

想审计/拦截所有工具调用 → 类型化事件

痛点 新需求："高危命令要弹审批框"。改 agent 循环加 if？碰核心。 让每个工具自查？重复 N 遍。这类需求的本质是横切关注点。

解法：广播通知，且选对分发模式就能做环绕拦截

// 核心派发用 waterfall（瀑布式，Koa 洋葱模型）：
const result = await ctx.waterfall('tools/call', input)

// 审批插件插入进来，不修改任何人：
ctx.on('tools/call', async (input, next) => {
  if (risky(input)) {
    const ok = await askUserApproval(input)
    if (!ok) return            // 不调 next() = 否决，链条到此为止
  }
  return next()                // 放行
})
  • emit 广播不等结果 · parallel 并发等齐 · serial/bail 排队跑首个非空胜出 · waterfall 环绕中间件。
  • 审批、审计、限流全是套在链上的洋葱皮。你家仓库里的 metaagent-bridge.mjs 的 approval 监听器就是活例。
🧪 实验 B：waterfall 洋葱链

关掉某个开关再跑一次；两条命令都试。 注意危险命令被否决时——工具本体从头到尾没被执行，这就是 next() 缺席的含义。

Station 5 · 接缝

把 bash 搬进云沙箱 → 能力接缝

痛点 想把整个执行环境搬进远程 VM：bash 工具、终端、LSP、文件读写…… 只要它们直接摸过 child_process 或 fs，就全都得动。

解法：底层访问收编成抽象服务键 + 同键只允许一个实现

# 换执行环境 = 只换清单里的提供方
- name: '@dsh/bash-local'     # 换成 ↓ 就全体上云
- name: '@ext/bash-e2b'
# ctx.fs 同理：fs-local ↔ fs-sandbox ↔ fs-e2b
解法 接缝 = 一个抽象服务键。Cordis 的重复注册守卫保证每个键在一个上下文只有一个实现， 于是消费方（bash/terminal/LSP 工具，它们 inject 的只是 'shell' 字符串） 在提供方更换时自动重启并拿到新实现——多米诺式整体搬家，工具代码零修改。 反过来读也成立：看到某能力像"装哪个插件"那样切换，背后必有一个接缝键。

⚡ 这就是 dsh README 那句「替换单个提供者就能改变整个产品」的全部机关。 回第 2 站的实验 A， 点「预设：云沙箱版」看这个多米诺现场发生。

Station 6 · 事件溯源

重启后什么都没了 → 会话即追加日志

痛点 进程一重启对话历史没了；想复盘 agent 中间干了什么，也拿不出依据。

解法：发生过的事都写成 append-only 日志，状态=回放，视图=投影

interface SessionEvent<T> {
  seq: number        // 单调递增序号
  time: number       // epoch 毫秒
  type: string       // 'user/message' | 'tool/result' | 'turn/end' ...
  data: T
  ignorable?: true   // 读到不认识的事件能否安全跳过
}
// Agent 循环照常干活，但每次状态变化都落一条事件。
  • 当前状态 = 从头回放日志推出来（崩溃恢复、跨机续聊都是"重新回放"）。
  • 任何视图都是同一条流上的投影：聊天气泡是一种投影，「轨迹」（轮次+耗时+用量）也是同一条流的另一种投影——UI 都不自建账本。
  • 注意两个层次：这里的 SessionEvent 是持久化事实账本；第 4 站的 Events 总线是进程内即时通知。一个是记账本，一个是喊话筒。

Station 7 · 组装层

几十个插件怎么分发 → 束、档案与双面架构

清单长了以后，dsh 加了两层纯配置概念和一条物理分界线，没有任何新机制：

  • 束（bundle）：可分发的半成品清单，如 dsh-base（骨架）、 dsh-web-app(+Web UI)。关键是束里插入的内容允许上层打补丁覆盖（patch overlay）—— 你的项目 patch 一行配置就能换掉 bundle 里的某一件。
  • 档案（profile）：用户存在本地的命名组合，相当于"我的 ~/.dsh 选了哪些插件"。
  • Host / Client 双面：Node 侧跑 agent 循环、LLM、工具执行（第 0~6 站的一切）； 浏览器侧只有 React UI + RPC 订阅。构建期强制隔离成两个程序集，仅共享类型声明。
点到为止 dsh Web 版的本质：Host 进程里第 0~6 站照常运转，浏览器只是一个订阅会话事件流画图的消费者—— 和你家 Electron 工作台通过 JSON-RPC 驱动 DSH 子进程完全同构。

两道自测题（先自己答，再展开）

① 为什么换掉 ctx.shell 的实现后，bash 和 terminal 工具一行都不用改？ 因为这两个工具没有 import 任何 shell 实现——它们只在 inject 里声明了字符串键 'shell'（第 2 站）。 接缝规则保证该键在每个上下文只有一个实现（第 5 站），于是换提供方时 Cordis 自动把它们连带重启并交给新实现（第 3 站的级联机制）。 三层机制咬合：声明依赖 → 同键单实现 → 卸载级联。
② 为什么轨迹视图敢声称"零 KV cache 影响、完全不碰 Chat 快照"？ 因为它是纯投影（第 6 站）：自己注册一组 target 专属的事件 Definition，从共享的 SessionEvent 日志独立组装出自己的快照模型； 既不发出任何模型请求（自然无 KV cache），也不读写 Chat 视图的状态。两个视图互不知晓、互不干扰，共同的数据源只有那份 append-only 日志。

学完想去哪个方向深挖，随时告诉我：fiber 调度细节、waterfall 错误语义、还是直接开工作台 Phase 1 移植。
