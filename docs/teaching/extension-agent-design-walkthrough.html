扩展 Agent 设计原则从“面板扩展”走向“宿主 Agent 能力单元”

先把讨论对象抽象对

书架、Git 面板、知识库和日报只是不同领域。我们要设计的是一种稳定的扩展单元，让它能拥有界面，也能安全地接入宿主 Agent。

痛点
如果扩展自己画聊天、自己请求模型、自己保存历史、自己执行写入，每个扩展都会重新实现一套 Agent 系统。
设计目标
宿主统一管理 Agent Session、消息流、工具循环、审批和恢复。扩展只贡献领域能力、上下文和界面。

扩展、插件和 Agent Session 分三层

三者解决不同问题。用户安装的扩展包、宿主内部的 Kernel 插件和运行中的 Agent Session 不应混成一个概念。

扩展包

可审核、可同步、可绑定工作区或项目。包含 views、tools、background、data 等。

Kernel 插件

宿主内部的装配单元。通过 Runtime Kernel 注册域、能力、事件和资源。

Agent Session

一次真实的模型交互。拥有历史、回合、工具调用、取消、恢复和 UI 投影。

宿主拥有 Agent Loop

扩展只描述业务能力。宿主负责把用户输入、模型请求、工具执行、流式输出和持久事件组织成可恢复的回合。

user message
  → prepare turn
  → model request
  → stream assistant
  → tool call
  → tool result
  → next step or turn end

扩展贡献工具和上下文

工具决定 Agent 能做什么。上下文决定 Agent 在这一轮应该看到什么。两者都需要声明、授权、预算和实例绑定。

工具

带 JSON Schema、权限类别、取消信号和结构化结果。写操作先生成提案，再提交。

domain.search
domain.proposeChange
domain.applyChange

上下文

按需读取当前选择、过滤器、视图状态和领域资源。上下文有大小上限，不能把整个数据集常驻 prompt。

context.describe()
context.read({ key, budget })

安全和生命周期是产品能力

扩展可以接近模型、数据和本机能力。治理面必须和功能面一起设计。

身份

实例、工作区、项目和会话由宿主绑定。模型参数不能选择目标。

权限

工具声明读取、写入和高风险操作。审批发生在宿主统一入口。

恢复

流式事件、取消、崩溃和重启都能分类，未知状态不自动重投。

设计原则扩展获得的能力宿主保留的责任
宿主拥有 Agent Loop声明工具和上下文模型、回合、事件、恢复
工具可无 UI 工作返回结构化领域结果决定何时显示 ChatSurface 或卡片
写入先提案后提交生成变更方案审批、事务、审计和回滚
实例边界优先使用当前实例数据身份、权限、生命周期和迟到结果
当前待决策
第一版可以先采用“每个扩展实例一条长期 Agent Session”。多线程、Agent 分叉、结构化 UI 和热更新建立在这条基础合同之上。
自测一：为什么不让每个扩展直接调用 llm.chat？

因为它会让每个扩展重复实现会话、工具循环、流式状态、取消、恢复和审批。宿主也无法统一治理这些行为。

自测二：为什么上下文提供器不能返回整个领域数据库？

因为模型上下文、权限和性能都需要有界。按需资源读取可以把选择状态、预算和访问记录留在宿主合同中。
