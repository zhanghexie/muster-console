自己动手，造一个「恰好够用」的 Agent Harness

Pi 是 Mario Zechner（badlogic）写的极简编码 Agent：口号是 “Adapt Pi to your workflows, not the other way around.” 它故意把"平台替你做主"的部分砍到最少，只留三样硬通货：统一各家 LLM 接口、一条不会写崩的 Agent 主循环、留足钩子让你自己改。

整个仓库是一个 monorepo，核心就三层积木：

packages/ai@earendil-works/pi-ai
统一多 provider 的 LLM API：消息格式、流式事件、工具调用全部归一
packages/agent@earendil-works/pi-agent-core
有状态的 Agent：工具执行、turn 循环、双队列插话、事件流
packages/coding-agent@earendil-works/pi-coding-agent
CLI 产品层：内置工具、扩展系统、会话持久化、压缩、TUI

本页的讲法：带你在每一站「从零造一个迷你版」——先看朴素做法为什么撑不住（红框），再引入 pi 的真解法（绿框），并映射回真实源码。前五站各有一个活的实验区，按钮随便按，控制台全是真的在跑逻辑。

① 统一接口→② 双轨消息→ ③ 主循环→④ 双队列→ ⑤ 钩子与扩展→⑥ 会话与压缩

键盘 ← / → 也可以翻页。所有代码示例的签名都对照真实源码（v0.84.3），只简化了错误处理和泛型。

第 1 站 · PACKAGES/AI

统一 LLM 接口：一条流喂饱所有模型

痛点 · 朴素做法
直接连 API 意味着每接一家就要学一套方言：Anthropic 的 SSE 是 content_block_delta， OpenAI 是 choices[0].delta；工具调用的 JSON 增量切片格式也完全不同。 更糟的是换模型 = 重写接入层 + 重写 UI 解析。自己玩玩可以，做产品撑不住一周。
解法 · pi-ai 归一化
pi-ai 把「发什么」和「收什么」各自收敛成一个类型： 发出去统一是 Context（systemPrompt + messages）； 收回来统一是 AssistantMessageEvent 异步事件流 （text_delta / thinking_delta / toolcall_delta / done / error…）， 流走完还能拿到底终消息 AssistantMessage——它的 content 是统一的块数组（文本块/思考块/工具调用块混排）。provider 差异被压在各自的 adapter 里。
// mini 版：不管 model 是 Anthropic 还是 OpenAI 还是本地 llama.cpp，调用形状完全一致
const models = createModels();
const model = models.getModel("anthropic", "claude-sonnet-4-6")!;

const stream = models.streamSimple(model, {
  systemPrompt: "You are a coding agent.",
  messages: [{ role: "user", content: [{ type: "text", text: "列出 src 下的文件" }] }],
});

for await (const ev of stream) {              // 统一的 AssistantMessageEvent 流
  if (ev.type === "text_delta") process.stdout.write(ev.delta);
  if (ev.type === "toolcall_end") console.log(ev.toolCall.name, ev.toolCall.arguments);
}
const msg = await stream.result();            // 底终消息：content 块数组 + stopReason

第 2 站 · AGENT 的记忆里能放什么

双轨消息模型：UI 看得爽，LLM 吃得下

痛点 · 朴素做法
会话记录如果只能存 LLM 认识的三种 role（user / assistant / toolResult），TUI 就没法记「bash 正在跑、已输出 12 行」这类过程性内容； 反过来如果把它们一股脑塞进 context 直接发给 API——provider 返回 400，role 非法。渲染需求和数据约束打架。
解法 · AgentMessage ∪ convertToLlm
pi 把会话消息放宽成 AgentMessage = 三种 LLM 消息 ∪ 应用自定义类型（TS declaration merging 扩展）， 会话里想存什么存什么；每次真正调模型前过两道闸： transformContext() 先做裁剪/注入，convertToLlm() 再把自定义类型过滤掉或翻译成合法消息。 LLM 看到的是干净的三轨流水，UI 和持久化享受的是富模型。
// convertToLlm 由应用自己实现（来自真实源码的类型契约示例）
convertToLlm: (messages) => messages.flatMap((m) => {
  if (m.role === "custom") return [{ role: "user", content: m.content }]; // 翻译
  if (m.role === "notification") return [];                                // 只给 UI 看 → 过滤
  return [m];                                                              // user/assistant/toolResult 直通
})

第 3 站 · AGENT 的心脏

主循环：stopReason 是唯一方向盘

痛点 · 朴素做法
手写 while(true){ ask(); runTools(); } 很快会遇到三堵墙： ① API 报错，整个 while 直接炸掉；② 回复顶到 token 上限被截断——半截 JSON 参数照常执行就是事故； ③ 工具一个个串行跑，批量任务慢得难受。
解法 · 双层循环 + 状态分支
pi 的 runLoop 用 stopReason 统一决策： error / aborted 收摊返回；length 触发保护——整批工具调用判失败（截断参数不可信！）； toolUse 执行完工具继续下一 turn；stop 走出内层，去外层看看有没有 follow-up。 工具默认并行执行，可全局或逐工具覆盖为 sequential。execute 里 throw 不会打崩循环——它被 catch 成 isError 结果喂回给模型。
// 摘自 packages/agent/src/agent-loop.ts runLoop()（简化版，形状一致）
while (true) {                                  // 外层：follow-up 让整体再起一轮
  let hasMoreToolCalls = true;
  while (hasMoreToolCalls || pendingMessages.length > 0) {   // 内层：turn 循环
    pendingMessages.forEach(m => context.messages.push(m)); // ← 第 4 站讲从哪来
    const message = await streamAssistantResponse(context);   // 问一次 LLM

    if (message.stopReason === "error" || message.stopReason === "aborted")
      return emit({ type: "agent_end" });                     // 出错收摊，不崩

    const toolCalls = message.content.filter(c => c.type === "toolCall");
    const batch = message.stopReason === "length"
      ? await failToolCallsFromTruncatedMessage(toolCalls)    // 截断 → 整批 fail
      : await executeToolCalls(context, message);             // 默认并行执行
    hasMoreToolCalls = !batch.terminate;
    batch.messages.forEach(r => context.messages.push(r));    // 工具结果回灌

    pendingMessages = (await config.getSteeringMessages?.()) || [];  // turn 边界问插话
  }
  pendingMessages = (await config.getFollowUpMessages?.()) || [];    // 快停了问追加
}

第 4 站 · 干活时如何听人话

双队列：steering 插话，follow-up 排班

痛点 · 朴素做法
任务跑到一半用户补一句「顺便把 config 也改了」。直接往 messages 里 push？那条消息会和正在流式输出的 assistant 消息犬牙交错， 而且当前批次的工具调用结果后面才到，模型看到的是乱序对话。等 agent 停了再输？用户白等三分钟。 另外 prompt() 能不能中途重入再来一发？不能，重入会把状态搅成麻花。
解法 · 两条队列 × 两个注入时机
pi 在 Agent 上开两条队列： steer(msg) —— 打断欲不强，排队等当前 turn 结束边界（工具批执行完毕后）注入，不打断手头的活； followUp(msg) —— 不着急的新任务，等 agent 即将空闲时接管，续上新一轮。 QueueMode（all / one-at-a-time）决定每个边界吃掉几条。而忙时直接调 prompt() 会被明确拒绝并提示用 steer/followUp——宁可拒绝也不糊状态。
// packages/agent/src/agent.ts
steer(message)    { this.steeringQueue.enqueue(message); }   // 干活时插话
followUp(message) { this.followUpQueue.enqueue(message); }   // 给下一段活排班

async prompt(input) {
  if (this.activeRun)                                        // 忙时拒绝重入
    throw new Error("Agent is already processing a prompt. Use steer() or followUp() ...");
  ...
}
// QueueMode: "all"（边界吃光整队）| "one-at-a-time"（每次只放最老的一条）

第 5 站 · 为什么 pi 能给自己写扩展

钩子与扩展系统：循环只留缝，产品全靠插件

痛点 · 朴素做法
「rm -rf 要先确认」「工具输出要盖水印」「文件改动要 stash」……这些团队规矩若硬编码进主循环或某个工具里， 循环就被污染成了某个公司的内部工具，别人没法复用；换个规矩就得 fork 整个仓库。
解法 · 两条缝 + 一个事件总线
循环层只留两条缝：beforeToolCall（返回 {block:true} 即拦截，短路不执行） 和 afterToolCall（逐字段覆盖执行结果）。coding-agent 层再把缝封装成扩展系统： pi.registerTool / registerCommand / on("tool_call"…)/ appendEntry， 放进 ~/.pi/agent/extensions/ 就热加载。官方文档第一句话是： "pi can create extensions. Ask it to build one." —— 这就是「自扩展」的含义。
// ~/.pi/agent/extensions/my-extension.ts —— 官方 quickstart 原型裁剪
export default function (pi) {
  // 拦截：高危命令必须人工确认
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");
      if (!ok) return { block: true, reason: "Blocked by user" };   // 短路：不执行
    }
  });
  // 注册新工具：刷新后立即可被 LLM 调用
  pi.registerTool({
    name: "greet", label: "Greet", description: "Greet someone by name",
    parameters: Type.Object({ name: Type.String({ description: "Name to greet" }) }),
    async execute(toolCallId, params, signal, onUpdate, ctx) {
      return { content: [{ type: "text", text: `Hello, ${params.name}!` }], details: {} };
    },
  });
}

第 6 站 · 收尾 · SESSION

会话是一棵树，上下文是个橡皮筋

两个工程常识级设计
① append-only JSONL 会话：每条 entry 一行 JSON（id / parentId / timestamp），崩溃即恢复；entry 之间的父子关系天然构成分支树， session header 还带 parentSession 指针，fork 出来的会话知道自己从哪来。
② Compaction：上下文逼近阈值时自动触发——旧消息折叠成一条 CompactionSummaryMessage （没错，正是第 2 站那类自定义 AgentMessage，靠 convertToLlm 决定怎么喂给模型），「动过的文件清单」跨压缩累计，干活连续性不断。

📝 自测三题

1️⃣ 为什么 stopReason === "length" 时要把整批工具调用判失败，而不是挑看起来完整的执行？
因为 token 截断是从流的中段砍断的，「看起来完整」无从判断——参数可能是被拦腰斩断的半截 JSON。与其带着不可信参数去执行危险操作（比如写文件），不如全部 fail，让模型收到错误说明后在下一轮重新发出完整参数。（agent-loop.ts:381 failToolCallsFromTruncatedMessage）
2️⃣ 用户在 agent 干活时发的消息，为什么不能当场 push 进 context？steer 队列选在哪个时刻注入？
此刻 LLM 正在流式产出 assistant 消息、可能还有一批工具在并行执行——半路插入会让本轮对话顺序错乱，且下一个 LLM 请求的材料还没凑齐。pi 选择在每个 turn 结束（工具批执行完、下一个请求开始前）的边界统一 drain steering 队列；一次放几条由 QueueMode 控制。
3️⃣ CompactionSummaryMessage 既存在于会话文件里，为什么不会把 LLM 请求搞挂？
因为它不是 LLM 协议里的 role，而是自定义 AgentMessage。每次调模型前 convertToLlm 会把它翻译成合法消息（比如作为对话开头的 user 摘要）或按策略过滤——「会话里能存什么」与「模型能看到什么」本来就是两套独立的口径。
