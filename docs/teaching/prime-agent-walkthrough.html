一起从零造一个"迷你 Prime Agent"

Prime Intellect 的 prime-agent 自称 Self-Improving RLM Harness。老规矩：每站一个真实痛点 → 朴素做法为何撑不住 → 引入概念 → 动手玩。

它的一句话哲学是 "一切皆代码"（Everything is programmatic）。对照你已经学过的 deepseek-harness「一切皆插件」——两大流派殊途同归：模型面只是壳，权威状态在宿主。

路线图

  • 第 0 站：传统 tool-calling 裸脚本（三个痛点埋雷）
  • 第 1 站：工具太多、数据太大 → RLM：唯一工具就是写 Python（prompt-as-a-variable）
  • 第 2 站：状态无处安放 → 持久 kernel：变量跨调用、跨 compaction 存活（🧪 实验A）
  • 第 3 站：模型直接碰钱太危险 → host_request 桥：可信操作留在宿主
  • 第 4 站：派活给子代理 → rlm() 只回凭证不回答案（🧪 实验B）
  • 第 5 站：agent 越干越歪 → Continual Harness：/refine 小步自改进（🧪 实验C）
  • 第 6 站：任务跑一半断线 → daemon/compaction/goal/heartbeat 同一条路
  • 🏁 总结：三范式对照表 + 自测题

Station 0

传统 tool-calling 裸脚本

// main.ts —— 每个 coding agent 的起点
const tools = [read_file, grep, bash, edit, web_search, /* …几十个 */]

while (true) {
  const reply = await llm.chat(messages, toolSchemas)   // 每轮都带全部工具 schema
  if (!reply.toolCalls.length) break
  for (const call of reply.toolCalls) {
    const output = await tools[call.name](call.args)
    messages.push({ role: 'tool', content: output })     // 结果整块塞回上下文
  }
}
痛点 ① 工具越多，每轮请求携带的 schema 越撑；每个工具都要单独设计、注册、让模型学会挑选。
痛点 ② read_file 返回什么，什么就整个进入上下文。想在一万个文件里找一行配置？先把一万个文件读进来。
痛点 ③ 上一轮解析好的中间结果，下一轮就没了——状态无处安放，只能反复重算或塞进对话历史。

记住这三个痛点。Prime Agent 的整个设计就是逐一回应它们。

Station 1 · RLM

工具太多、数据太大 → 唯一工具是写 Python

核心翻转 Prompt-as-a-variable：上下文不再是一堆消息 + 工具结果，而是 kernel 里的变量。 内置模型工具只剩一个 ipython——读改文件、跑命令、调技能、派子代理，全是模型写 Python。 
# 模型在持久 Python kernel 里找一行配置——不用把仓库读进上下文
from pathlib import Path

hits = [p for p in Path(".").rglob("*.toml")
        if "max_workers" in p.read_text()]
print(hits)          # 只把结论 print 给模型，海量中间数据留在变量里
  • 痛点① 消解：没有几十个工具 schema 了——能力 = kernel 里可调用的函数（技能就是 import 名）。
  • 痛点② 消解：海量数据留在变量里，模型按需 print 结论。上下文给方向，kernel 存事实。
  • 官方论文称这是 RLM（Recursive Language Model）：工具与子代理都是"程序化调用"。
留下的痛点③ Python 变量默认活在一次进程里。任务跨几十轮、窗口满了要压缩历史、终端断了再连……状态怎么活下来？ → 下一站。

Station 2 · 持久 Kernel

状态无处安放 → 变量跨调用、跨 compaction 存活

解法 kernel 是持久 REPL：变量、导入、解析结果跨工具调用存活；compaction 压缩对话时特意保住 kernel 状态； 会话还可把命名空间 snapshot/restore 成 kernel-state.dill，进程重启也能复活。 
# kernel 与 TS 宿主之间的 stdio 协议（每行一个 JSON 对象）
requests   execute · interrupt · host_reply · snapshot · restore · list_names · shutdown
events     ready · stdout · stderr · result · display · host_request · error · done

Station 3 · Host Bridge

模型直接碰钱太危险 → 可信操作留在宿主

痛点 如果模型面什么都能干——调 provider、写转录、改调度——一个被污染的技能包就能烧你的 API 额度、篡改会话历史。
解法 · typed host_request Python 侧是纯 shim（官方原话：不调 provider、不实现 agent loop）。凡属权威状态的操作， 都以 rlm.host_request("rlm.run" | "goal.get" | …) 事件发回 TS 宿主，宿主校验后执行， 用 host_reply 带回结果。模型目录元数据可以过桥，auth store 永不过桥。 
# Python 侧发起派活（shim），真正建子会话的是 TS 宿主
handle = await rlm("inspect the API", name="api-reviewer")
# → kernel 发出 host_request(rlm.run)
# → 宿主校验深度 RLM_DEPTH < RLM_MAX_DEPTH、解析模型
# → 宿主 admission 后 host_reply 带回 handle；cell 可 await 而不阻塞 kernel 其他任务
  • 普通 Python cell 串行（一个 kernel 一个 namespace）；子代理并发 = 各自独立 host request + 独立 child runtime。
  • 请求的模型不可用 → spawn 直接失败，绝不静默换模型。
📖 源码指引 src/core/kernel/repl-manager.ts ← stdio 协议与 host-request 分派 prime-agent-runtime/src/rlm/ ← Python 侧 shim（无 agent loop）
Station 4 · 子代理

派活给子代理 → 只回凭证，不回答案

朴素做法的坑 让 rlm() 等子代理跑完并返回完整回答？父上下文立刻被子代理的中间过程撑爆， "递归"变成"上下文传染"，并行也无从谈起（还都卡在等待上）。
解法 admission handle：rlm() 在宿主收录任务后立即返回 {rlm_child_id, name, session_dir, model}——永不包含答案。 子代理干完活经 agent_message.send(receiver_role="parent") 或写文件回来； 想并行就连续 spawn 几个然后结束回合。 
# 父代理一回合派出三个独立子代理（深度默认封顶 2：root→child→grandchild）
api_review = await rlm("Review the public API", name="api-reviewer")
test_review = await rlm("Review the tests",   name="test-reviewer")
audit       = await rlm("Slow audit",          name="audit")
# 然后结束回合。子代理各用各的上下文，结果作为普通消息在未来回合到达。
🧪 实验 B：spawn 三连

父上下文（只有 handle 和消息，没有子代理内部过程）

父 turn usage：input 0 tok · output 0 tok

子代理自己的世界（父看不见）

尚无子代理

连续点三个 spawn：handle 立即回来（没等任何结果）。子代理在自己上下文里跑几十轮——父完全看不见。 结果稍后以 agent_message 到达，且usage 异步归并进父 turn（看左下计数）。点「结束回合」体会官方口号：spawn 完就走，别等。

Station 5 · Continual Harness

agent 越干越歪 → /refine 小步自改进

朴素做法的坑 「让 agent 改自己的系统提示词」——一次跑偏，永久跑偏；改坏了没法回退；谁改的、凭什么改，全无记录。
解法 · 状态账本 + 证据编辑 rlm.harness 是持久账本：4 种 kind（prompt 备注 / memory / skill 描述 / 子代理规格） × 2 种 scope（会话级 harness_state.json / 全局 ~/.prime/agent/harness/）。 /refine 审视当前轨迹，应用小步、有证据的 create/update/delete； 每次编辑记录快照可回滚；base system prompt 永不可变——自改进=积累经验层，不是改写核心。
🧪 实验 C：harness 账本 🔒 base system prompt 不可变

点「/refine」：它从轨迹里找证据（比如用户两次纠正提交信息格式），生成三条小编辑 → 「应用」后账本变化且快照入栈 →「回滚」原样恢复。base prompt 的锁从头到尾没动过。

📖 源码指引 prime-agent-runtime/src/rlm/harness.py ← 状态模型刻意小 harness/harness_state.json（会话级）· ~/.prime/agent/harness/（全局） 外部修改自动重载 ← kernel 写与 /refine 写互不覆盖
Station 6 · 长时运行

任务跑一半断线 → 所有入口走同一条路

  • daemon worker：会话跑在 daemon 进程里，终端断了照跑，prime-agent attach 重连。
  • auto compaction：contextTokens > window − reserve(16k) 触发； 保最近 ~20k 消息 + kernel 状态；/compact [指令] 可定向摘要。
  • persistent goals：goal.create("ship the release", token_budget=200000)， 预算记账，未完成自动续跑。
  • heartbeat / schedule / autonomous：定时或有界自主地重新进入会话。
  • agent 间直接通信：运行中的 agent 互发消息编排，不必经用户转发。
点睛 从会话队列往后，用户消息、heartbeat、cron、goal 续跑、别的 agent 的消息，走同一条执行与持久化路径。 所以"后台跑一整夜"不是特殊功能，只是换了个入口的普通回合。

Wrap-up

🏁 三范式对照 + 自测

传统 tool-callingdsh（一切皆插件）prime-agent（一切皆代码）
模型能力扩展注册工具 schema插件往 ctx 键注册kernel 里 import 的函数/技能
组合单位代码里写死cordis.yml 配置行Python 语句（编程式）
上下文策略工具结果整块塞回事件溯源 + 投影数据留变量，print 结论
子代理无原生概念插件可再入（subagent 系统）rlm() 原生调用，只回 handle
自改进手改提示词束/档案打补丁/refine 小步编辑 + 快照回滚
共同底线模型面只是壳；凭证/转录/调度等权威状态留在宿主

自测三题（先自己答，再展开）

① 为什么 rlm() 敢"只回 handle 不回答案"？结果靠什么回来？ 因为结果通道与调用通道彻底分离：调用只做 admission（宿主收录任务、记账、注册），答案经 agent_message.send(receiver_role="parent") 或文件在未来回合作为普通消息到达。 这样父上下文只增加一行 handle 和最终结论，子代理几十轮内部过程永不传染；多个 spawn 天然并行。
② compaction 压掉旧对话后，模型为什么还能用之前解析好的数据？ compaction 只摘要对话条目；kernel 是独立进程里的持久命名空间，不在压缩范围。 极端情况下进程没了，会话 artifacts 里的 kernel-state.dill 快照 + restore 请求可复活命名空间。 这就是"状态为跨轮次设计"。
③ /refine 改坏了怎么办？它为什么不碰 base system prompt？ 每次编辑都记录 before/after 快照，可精确回滚到任意一步。base prompt 不可变是刻意的安全边界： 自改进只允许在补充状态账本（4 kind × 2 scope）上小步、有证据地进行——跑偏最多污染经验层，回滚即愈，核心永不被劫持。
